# Досягнення без Blaze

Активна версія працює без Cloud Functions. Браузер обчислює автоматичний прогрес із збережених даних користувача; Firestore Rules перевіряють права, каталог, фіксовані бали, вітрину й згоду на участь у рейтингу. Не потрібно підключати білінг. Залишаються стандартні квоти Firestore Spark.

Адміністратор видає й відкликає медалі в адмінці. Ручні нагороди зберігаються окремо від автоматичних; звичайний користувач не може видати собі приховану медаль. Повторна видача не подвоює бали, а відкликання ручної видачі не забирає автоматично отриману медаль. Журнал видачі не можна змінити або видалити з клієнта. Адміністратор не може сам увімкнути чужу участь у рейтингу.

Прогрес оновлюється на сторінці досягнень та після збереження відповідних даних у застосунку. Дні активності рахуються раз на календарний день UTC, починаючи з цієї версії. Для спільних тренувань обидва учасники мають відкрити оновлений застосунок: кожен записує підтвердження власного завершення. Правила перевіряють актуальну сесію при читанні підтвердження, тому видалений результат більше не враховується. Чужі журнали тренувань не відкриваються.

Обмеження: автоматичні факти обчислює клієнт. Правила перевіряють відповідність медалей фактам і фіксовану суму балів, але не перераховують усю історію тренувань. Це рейтинг даних, заявлених користувачами, а не незалежна перевірка спортивних результатів. Адміністративні нагороди та доступ до чужих даних захищені правилами.

## Публікація

Тижневі цілі та післятренувальні записи самопочуття зберігаються у приватних колекціях `weeklyGoals` і `workoutReflections`. Власник облікового запису може задати ціль на поточний тиждень, переглянути попередній підсумок, порівняти завершене тренування з попередніми та відмітити складність, енергію й нотатку. Адміністратор та інші користувачі не мають клієнтського доступу до цілей і самопочуття.

Спільний виклик `gymChallenges` має двох підтверджених GymBro, період і ціль на кожного. Другий учасник має прийняти запрошення; змінити умови після створення не можна. Кожен публікує лише власну кількість виконаних тренувань. Коли обидва досягають цілі, нараховується медаль «Виклик прийнято» (100 балів, один раз). При зміні журналу прогрес перераховується після синхронізації; для отримання актуального прогресу партнера є кнопка «Оновити».

Історія `achievementEvents` зберігає дату додавання медалі, джерело й причину. Для нової адміністративної видачі примітка явно позначена як видима одержувачу. Старі приватні адміністративні примітки не переносяться в повідомлення. Наявні медалі додаються в історію під час першої синхронізації цієї версії; це дата додавання в історію, а не відновлена дата давнього отримання. Події не дублюються при повторній видачі; їхній зміст і дата незмінні, можна лише позначити прочитаними. Нагороди з’являються у сповіщеннях та на сторінці досягнень.

Конструктор блоків у власному профілі зберігає порядок і видимість у `publicProfiles/{uid}/layout/display`. Інші бачать обране компонування, але приватні цілі, самопочуття, заміри, журнал і графік не стають публічними через налаштування блоків. Наявні налаштування приватності статистики та рекордів залишаються чинними.

Додаткові можливості тренувань:

- Рекорди за точною кількістю повторень: готові варіанти 5, 8, 10, 12 та введення власного значення. Видно у власному профілі; нові рекорди на стандартні кількості відзначаються в підсумку тренування. Розминка, невідома вага та майбутні записи не враховуються. Це записані результати, а не розрахункова максимальна вага.
- Тимчасова заміна зберігається тільки в сесії (`replacements`), містить початкову вправу й причину. Вага для нової вправи та її підходів обнуляється, чернетка попередньої вправи не переноситься. До появи результатів можна повернути початкову вправу; після записаних підходів заміна та повернення блокуються. Програма не редагується.
- Річний календар активності розділяє основну програму (синій), домашні комплекси (помаранчевий), обидва типи в один день (двоколірний) та старі записи без збереженого типу (сірий). Є фільтри й перехід до дня в місячному календарі. Нові сесії зберігають `scope`, тому тип залишається відомим після видалення програми; старі сесії визначаються за програмою, якщо вона ще існує.
- Опитування `meetingPolls`: два GymBro, 2–6 майбутніх варіантів за київським часом, окремі змінювані відповіді у `votes/{uid}`. Автор спочатку голосує за всі власні пропозиції; другий учасник може обрати кілька або жодного варіанта. Автор закриває голосування після відповідей обох. Вибраний час переноситься у звичайне запрошення; повторне надсилання створює одну сесію, а GymBro окремо приймає запрошення. Учасники не можуть голосувати за іншого, сторонні не читають опитування; після закриття відповіді незмінні.

```powershell
npm run build:achievements
npm run prepare:achievement-rules
firebase deploy --project nexus-gymb --only "firestore:rules,firestore:indexes"
```

Команда підготовки правил оновлює блоки Spark-досягнень, можливостей тренувань, опитувань, приватних нотаток до вправ і правил історії сповіщень. Решта дозволів у локальному файлі зберігається. Індекси `gymChallenges.members + createdAt` та `meetingPolls.members + createdAt` мають перейти в стан READY перед публікацією клієнта.

Сайт публікується звичайним workflow GitHub Pages. `firestore.rules` залишається локальним згідно з `.gitignore`; генератор змінює лише блок досягнень у наявній копії правил. Код у `functions/` збережено як попередню реалізацію; він не використовується сайтом і не включений у Firebase deployment configuration.

## Перевірка

```powershell
npm test
npm run test:achievement-rules
```

Для браузерної перевірки разом із Firestore Emulator встанови `QA_BROWSER_PATH` у шлях до Chrome. Перевірка використовує справжні клієнтські операції Firestore, тестові акаунти й емулятор; до робочої бази тестові дані не записуються.

Особисті нотатки та експорт результатів:

- `users/{uid}/exerciseNotes/{encodeURIComponent(exerciseKey)}`: приватний текст до 2000 символів. Ідентичність вправи зберігається між тренуваннями; для власних вправ без ID використовується нормалізована назва. Читання, запис і видалення дозволені тільки власнику, включно з забороною читання адміністратором через клієнт сайту. Нотатка доступна у деталях вправи та в простому, змішаному й розширеному режимах тренування. Порожнє поле видаляє запис. Редактор перед відкриттям перечитує запис із сервера, щоб помилка завантаження не спричинила перезапис порожнім текстом.
- У підсумку завершеного тренування є попередній перегляд картки та завантаження PNG/PDF. Експорт працює локально, без CDN, Cloud Functions і передачі файлу на сервер. Обидва формати містять однакові вправи, згруповані результати підходів, час, обсяг та рекорди. PDF використовує растрові сторінки A4 з підтримкою української; довгі тренування автоматично розбиваються на сторінки. PNG об’єднує сторінки в одне зображення; для зображення понад 16000 px пропонується PDF. Особисті нотатки й записи самопочуття не експортуються в картку.

Історія сповіщень:

- Прочитані події досягнень і звичайні сповіщення відображаються разом за часом та залишаються після перезавантаження. Перші 100 звичайних сповіщень слухаються наживо; старіші завантажуються сторінками по 50 без видалення з бази. Позначення завантажених прочитаними обробляє будь-яку кількість записів пакетами по 100.
- Нові соціальні події використовують окремі `event_UUID` документи. Повторне додавання GymBro зберігає попередні заявки й прийняття, а не перезаписує їх. Правила перевіряють дію-джерело, адресата й автора; змінювати існуючу подію може тільки одержувач і лише поле `read`. Старі ідентифікатори підтримуються для першого створення старими клієнтами. Автоматичного видалення сповіщень у клієнті немає; блокування автора не прибирає історичні записи.
- Ціль на тиждень і спільні виклики на головній розташовані після основної програми та останніх тренувань. Новий header і форми входу/реєстрації адаптовані до вузьких екранів. Динамічний фон авторизації працює через CSS, із підтримкою `prefers-reduced-motion`.

Header профілю:

- У наявному редакторі оформлення (`Налаштування → Оформлення → Header для відвідувачів`) є стандартний режим, палітра профілю й власні кольори, назва до 32 символів, суцільна/скляна/градієнтна поверхня та три форми кутів. Як і решта редактора, можливість доступна власнику сайту або користувачам із `profileCustomization`.
- Параметри `header*` зберігаються всередині `publicProfiles.appearance` і перевіряються правилами разом із доступом до кастомізації. Окремого читання Firestore немає. Старі профілі без цих параметрів використовують стандартний header. Напис задається як текст, без HTML чи посилань; кнопки та переходи залишаються звичайними.
- Header застосовується лише на доступній сторінці профілю. Він скидається для головної, інших розділів, обмеженого профілю та наступного профілю зі стандартним оформленням. Кольори тексту й акцентних підписів автоматично підбираються для читабельності. Глобальна тема відвідувача не змінюється.
- `scripts/update-profile-header-rules.mjs` додає поля й перевірки лише до `validAppearance`. Він включений до `prepare:achievement-rules`; решта робочих правил зберігається.
